A routing change ships: pick the chain with the lowest block time, because faster blocks mean faster settlement. Polygon produces a block every 2 seconds against Ethereum's 12. Transfers start routing to Polygon. Median settlement time goes from 20 seconds to **256 seconds**. The metric that was supposed to improve got twelve times worse, and the code does exactly what it was designed to do — because the model it was built on was wrong.

<Warning>
**Symptom:** After routing transfers to the chain with the shortest block time, median settlement time jumped from 20 seconds to 256 seconds. The routing logic was correct. The model behind it was not.
</Warning>

## The model that was wrong

The reasoning is intuitive and completely wrong:

> A transaction settles when it is in a block. Blocks arrive every *n* seconds. Therefore lower *n* means faster settlement.

The first sentence is the error. **A transaction is not settled when it is in a block.** It is settled when the probability of that block being reorganised out of the chain has fallen far enough that you are willing to pay someone real money against it. Inclusion is not finality. Finality is a confidence level about permanence.

<Note>
**Settlement time is `block_time × confirmations_required`, and these two numbers are inversely related by design.** Chains with fast, cheap blocks make each individual block less expensive to orphan — so they require more of them to reach equivalent confidence in the outcome.
</Note>

## The five chains that prove it

| Chain | Block time | Confirmations | Settlement window | Ratio to Ethereum |
| --- | --- | --- | --- | --- |
| Solana | 400 ms | 32 | ~13 s | 0.09× |
| Base | 2 s | 10 | 20 s | 0.14× |
| Tron | 3 s | 19 | 57 s | 0.40× |
| Ethereum | 12 s | 12 | 144 s | 1.00× |
| **Polygon** | **2 s** | **128** | **256 s** | **1.78×** |

Polygon and Base have **identical block times** — both 2 seconds. Base settles in 20 seconds. Polygon takes 256. The entire difference is in the finality depth, and a router that reads only block time cannot see it at all.

Sort that table by block time and you get Solana, Base, Polygon, Tron, Ethereum. Sort it by what the customer actually experiences and you get Solana, Base, Tron, Ethereum, Polygon. **Polygon moves from third-fastest to last.**

## Why the naive model is so persistent

Block time is the number everyone publishes. It is on the landing page, in the comparison tables, and it is a single scalar that looks like "speed." It is measurable, marketable, and easy to reason about.

Finality depth is a security parameter that lives in operational documentation and varies by who you ask. There is no single authority publishing the canonical "confirmations required" for each chain — exchanges set their own thresholds, and they set them based on the value at risk on their specific platform.

<Warning>
**Finality depth is a policy choice, not a physical constant.** The numbers in the table above are the values Arc simulates, chosen to reflect published guidance for typical transfer sizes. A business with lower risk tolerance would use higher confirmation counts and see different settlement times. This is exactly why it belongs in configuration — alongside block time, not in an engineer's mental model of the chain.
</Warning>

## How Arc models this

Chains carry their finality characteristics together as configuration, so the settlement window is derived rather than assumed or stored separately:

```ts
CHAINS = {
  polygon: { blockTimeMs: 2_000, finalityDepth: 128, ... },
  base:    { blockTimeMs: 2_000, finalityDepth: 10,  ... },
  tron:    { blockTimeMs: 3_000, finalityDepth: 19,  ... },
  solana:  { blockTimeMs: 400,   finalityDepth: 32,  ... },
  eth:     { blockTimeMs: 12_000, finalityDepth: 12, ... },
}
```

`selectChain` then scores on the derived settlement window, alongside fee, weighted by a configurable speed preference:

```text
score = normalise(settlementTime) × speedWeight
      + normalise(fee)            × (100 − speedWeight)
```

<Note>
High speed preference picks **Base**. Low speed preference picks **Tron** — cheaper, and 57 seconds is acceptable for a transfer that is not time-critical. Neither ever routes to Polygon on speed grounds, because the model can see what block time alone hides. Both terms are normalised before weighting, because adding seconds to gas units is meaningless arithmetic.
</Note>

## The per-chain differences that also matter

Once you model finality correctly, the other per-chain differences become visible — and they are not uniform noise:

| Chain | Distinguishing characteristic | What it costs the saga |
| --- | --- | --- |
| Solana | Highest transaction drop rate — mempool eviction | Transactions that never mine and cost nothing; different compensation path than a revert |
| Polygon | Deepest historical reorgs | A transaction counted as included can return to `pending` |
| Ethereum | Highest fee volatility | Network-fee estimates age fastest and must be refreshed |

<Note>
This is what "chain-agnostic" has to mean to be worth anything: not that all chains are interchangeable, but that **their specific differences are modelled** and the choice is made per transfer behind a single interface. If all chains behaved identically, the abstraction would be decoration.
</Note>

## The easy mistake to make in the settle step

Even with correct routing, the `settle` implementation itself can lie. The naive version:

```ts
await chain.broadcast(tx);
// no error thrown — must be settled!
```

Broadcasting without error means the transaction reached the mempool. It says nothing about block inclusion, nothing about finality, and nothing about whether the transaction reverted on-chain with a successful receipt code.

Arc's `settle` step re-reads the transaction after broadcast and **requires `final`** before advancing the saga:

```ts
const receipt = await chain.waitForFinality(txHash);
if (receipt.status !== "final") {
  throw new ChainError("Transaction did not reach finality", { retryable: true });
}
```

Checking `final` rather than "no error was thrown" is the difference between confirming settlement and confirming submission. The wrong version looks completely correct until the day a transaction is dropped from the mempool or a block is reorganised.

## The lesson

<Steps>
  <Step title="The published metric is rarely the operative one">
    Block time is measurable, publishable, and marketable. Settlement time is what the customer experiences and what the system must guarantee. When these diverge, optimising the visible metric moves the invisible one in the wrong direction.
  </Step>
  <Step title="Derive composite metrics; never store them separately">
    `settlementWindow` is computed from block time and finality depth at query time, so it cannot drift out of sync with either input. Storing it as a third configuration field would guarantee that it eventually disagrees with the values it was derived from.
  </Step>
  <Step title="Model the differences that matter, not the ones that are easy">
    An abstraction over five chains that treats them as interchangeable is decoration. An abstraction over five genuinely different chains, whose differences are visible to the router, is doing real work.
  </Step>
</Steps>
